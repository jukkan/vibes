Plausible RCE:from a hidden endpoint
to a cryptominer.

A routine server health check found a miner inside my analytics container. Here’s the vulnerability behind it, and what it took to recover.

Jukka Niiranen · 2 October 2026 · approximately 4 minutes
Affected CE releases3.0.0–3.2.0
First patched release3.2.1
Underlying vulnerabilityCVE-2026-8467

What went wrong?

Plausible shipped a developer component preview at /storybook. Its Phoenix Storybook dependency could turn visitor-supplied input into code executed on the server. No account or login was needed. That’s remote code execution (RCE). [1]

The code ran with the application’s permissions inside its container. That puts accessible credentials and data at risk; Docker isolation alone cannot protect them. Plausible’s fix removed the endpoint. [2]

My installation

The visible symptom

Unexpected CPU and memory use led to a cryptocurrency miner in the Plausible container. Suspicious requests to /storybook and untrusted code in persistent application storage were consistent with this vulnerability.

The deployment was still on 3.2.0. Similar miner incidents appear in the GitHub discussion, but that does not establish a shared attacker.

  2. Input becomes codeThe preview evaluates a crafted value.
  3. Application accessCode runs with the app’s permissions.

What recovery involved

Killing the miner would leave the entry point and compromised files behind. We treated the application environment as compromised.

  1. Contain

    Stopped the application and disabled its automatic restart. Analytics collection paused while we investigated.

  2. Preserve & back up

    Retained the old container and suspect files. Backed up both databases and tested restores in isolation before relying on the backups.

  3. Rebuild cleanly

    Deployed the patched 3.2.1 image with fresh application storage. Kept existing database data; copied no suspect executable files. Also blocked the old endpoint at the proxy.

  4. Rotate access

    Replaced application secrets, database credentials, account credentials and API access; revoked old sessions and tokens. Updated dependent connections too.

  5. Verify the whole pipeline

    Checked login, historical reports and endpoint removal. Sent a labeled test pageview and confirmed it reached storage. Checked processes and resource use.

  6. Close maintenance gaps

    Reduced database privileges and tightened container settings. Added daily database backups, verified off-host copies and a recurring upstream release check.

A working dashboard can hide broken collection

Credential rotation initially left an internal database connection out of sync. Historical reports worked and the collector accepted requests, but new events were not saved. A successful HTTP response is not proof that analytics reached the database.

Recovery has limits. Targeted checks found no evidence of host escape. They do not prove that credentials or data were never read. Service was restored; historical exposure remains uncertain.

If you self-host Plausible

Check the version of your running container. OS security updates do not update a pinned Docker application. If affected, move to a maintained patched release; 3.2.1 is the first fix for this issue. Block /storybook as an immediate mitigation if an upgrade must wait. Review logs, processes and unexpected connections. Suspicious activity calls for compromise recovery and rotation of accessible secrets. [2]
